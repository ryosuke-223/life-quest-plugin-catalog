# ローカル線親カタログ完全性設計

## 目的

「ローカル線の旅」は、親プラグインが経営会社ごとのグループと路線項目を持ち、子プラグインが1経営会社の駅実績を路線グループ単位で管理する。子の駅訪問は親の対応する路線へ集計し、子が未導入の路線は親で手動入力する。

今回の変更では、この既存の路線単位の管理を維持したまま、子プラグインを追加したときに親側の会社グループ・路線項目・`routeLinks` が不足しないよう、カタログ検証で登録漏れを検出する。

## 現在の契約

- 親は `kind: "collection"` の `local-railways` である。
- 親の `groups` は経営会社、親の `items` は路線である。
- 親の `collection.routeLinks` は、親の路線項目と子プラグインの路線グループを結ぶ。
- 子は `parentPluginID: "local-railways"` を持つ `kind: "standard"` プラグインである。
- 子の `items` は駅、子の `groups` は路線である。
- 子の駅訪問は、対応する親路線へ `estimated` または `confirmed` として集計される。
- 親で子未導入の路線を手動訪問済みにできる。
- 親の「リアス線」などの路線項目は管理対象なので削除しない。

## 完全性ルール

カタログ検証時、次を必須とする。

1. `collection.children` に列挙された子プラグインは、存在する `standard` プラグインで、親の `parentPluginID` と一致する。
2. 子プラグインの全 `groups`（路線）は、親の `collection.routeLinks` に同じ `childPluginID` と `childGroupID` で1回ずつ登録される。
3. 各 `routeLink.routeID` は親の既存 `items` に対応し、親路線は重複リンクされない。
4. 同じ子プラグインの全 `routeLinks` は、親の路線項目に設定された同じ `groupID` を参照する。その `groupID` は親の `groups` に存在し、これが子プラグインの経営会社との対応を表す。
5. 未対応路線は親の手動管理項目として残せるが、子プラグインに存在する路線グループを未リンクのままにしてはならない。

これにより、子プラグインだけを追加して親への路線登録を忘れたカタログを公開前に拒否できる。現時点の三陸鉄道1路線と東京メトロ9路線は、このルールを満たしている。

## 変更範囲

- `scripts/validate_catalog.py` に、子プラグインの全路線グループが親の `routeLinks` に登録されていることを検証する処理を追加する。
- 検証スクリプトのテストに、未リンクの子路線を拒否するケースと、現在の親子カタログを受け入れるケースを追加する。
- `RAILWAY_PLUGIN_DATA_SOURCES.md` とカタログREADMEに、子プラグイン追加時に親へ会社グループ・全路線・リンクを同時に追加する手順を記載する。
- JSONの公開データは、現在の親路線を削除せず、既存の親子対応を維持する。
- Swiftアプリの保存形式、集計処理、画面、子プラグインの駅データは変更しない。

## 検証

- `python3 -m unittest discover -s scripts -p 'test_*.py'`
- `python3 scripts/validate_catalog.py`
- `python3 scripts/build_catalog.py` の後に `git diff --exit-code -- catalog.json` で生成カタログが同期していることを確認する。
- 現在の親子データで、三陸鉄道の全1路線と東京メトロの全9路線がリンク済みであることを確認する。
